# Design Goals for draft-pqc-scep

Sources: RFC 8894 (SCEP), RFC 9480 (CMP Updates), RFC 9810 (CMPv3).
G1–G3 come from the authors' meeting task list; G4–G14 come from comparing these RFCs.

| # | Design goal | Problem in RFC 8894 | What CMP does (RFC 9480 / 9810) | Open points for our draft |
|---|---|---|---|---|
| **G1** | **Allow KEM protection by letting the server optionally have a separate encryption cert** next to its signing cert, with GetCACert returning both *(task 1)*. This is an optional upgrade. A single dual-use CA cert remains allowed, and the CA cert may still sign SCEP messages. | §2.1.2 assumes one CA cert with both digitalSignature and keyEncipherment. An ML-KEM key cannot sign, so a post-quantum CA cannot use one cert for both jobs. Appendix A renamed "RA certificates" to "intermediate CA certificates" and never defined a separate encryption cert. | 9810 §5.3.19.1 lets the client fetch a separate "CA Protocol Encryption Certificate" (`id-it-caProtEncCert`). 9480 §2.2 defines EKUs (id-kp-cmcRA, id-kp-cmcCA) to show the CA has delegated a role. 9810 §5.3.19.14 adds a genm for getting CA certs. | Reuse the `x-x509-ca-ra-cert` certs-only bag (§4.2.1.2). Define how the client tells the two certs apart: KU digitalSignature vs keyEncipherment, and possibly an EKU. The encryption cert must chain to the authenticated CA cert (§2.2). GetNextCACert (§4.7) must also return the new encryption cert. |
| **G2** | **Encrypt requests with EnvelopedData and KEMRecipientInfo** (RFC 9629, with ML-KEM per RFC 9936) *(task 2)* | §3.1 offers only KeyTransRecipientInfo (RSA) or PasswordRecipientInfo (challengePassword). | 9810 §5.2.2 adds RFC 9629 KEM as a fourth key-management option when the recipient's key is a KEM key with keyEncipherment. | The recipient is the encryption cert from G1. Identify it with issuerAndSerialNumber or subjectKeyIdentifier. State the KDF and wrap algorithm (RFC 9936 already fixes these per parameter set). |
| **G3** | **Enrol client KEM keys with a defined POP** *(task 3)* | PKCS#10 (§3.3.1) and the outer SignedData (§2.3) are both signed by the key being certified, which a KEM key cannot do. SCEP has no certConf (§7.4). | 9810 §4.3.4 and §5.2.8.3: a **direct** challenge (popdecc/popdecr, which adds a round trip) or an **indirect** encrypted cert (encrCert plus certConf certHash, the preferred option). Either way the request signals the method in POPOPrivKey.subsequentMessage. | Options 3a (direct challenge), 3b (indirect, encrypted cert) and 3c (sign the KEM CSR with an EE signing cert) are still open. SCEP's lack of certConf weakens 3b. |
| G4 | **Encrypt responses to clients whose keys cannot encrypt** (ML-DSA, SLH-DSA, ECDSA, EdDSA) | For a non-RSA key, §3.1 falls back to PasswordRecipientInfo with challengePassword. That doesn't work for renewals and gives only password-level confidentiality. | 9810 §5.1.3.4 lets the shared secret from one KEM operation protect every later message in the same transaction. The KDF context is `KemOtherInfo{"CMP-KEM", transactionID, kemContext}`, which separates keys from different transactions. | The draft derives a response key from the request's content-encryption key (CEK) using HKDF and the transactionID. Still to define: which RecipientInfo type carries it (KEKRecipientInfo seems the obvious fit), a fixed label string as CMP does, and the undefined "kemResponse attribute". |
| G5 | **Response key across polling** | After PENDING, each CertPoll (§3.3.3) is a new message with a new CEK. §5.2 prefers resyncing with a new PKCSReq. | CMP keeps the shared secret key for the whole transaction. | Say which key encrypts a SUCCESS that follows PENDING: the original PKCSReq key (the CA has to keep state) or the latest CertPoll's CEK (stateless, preferred). |
| G6 | **Capability advertisement with normative GetCACaps keywords** | §3.5.2 defines no KEM keywords. The "SCEP CA Capabilities" registry is Specification Required. | 9810 §7: the client uses pvno cmp2021 only when it needs EnvelopedData. | Register keywords such as `ML-KEM-768`, plus signature-algorithm keywords if needed. |
| G7 | **Downgrade resistance** | §7.5: GetCACaps is unauthenticated, so an attacker can strip the KEM keywords and force a fall back to RSA key transport or a challengePassword. | n/a (CMP is protected end to end) | Extend the §7.5 advice: a client configured for PQC MUST NOT fall back. Consider a signed indication of support, such as the KU on the encryption cert in the authenticated chain. |
| G8 | **PQC signatures on SignedData** for client, server and GetNextCACert | MTI is SHA-256 with RSA-era assumptions. The CertRep signer is the CA key. | 9480 §2.10 / 9810 §5.3.18: optional hashAlg in certConf because PQC signature algorithms may not imply a hash. | Reference the ML-DSA and SLH-DSA in CMS specs. The client checks that the CertRep signer is the G1 signing cert (and possibly its EKU). |
| G9 | **Algorithm profile and MTI** | MTI is AES128-CBC and SHA-256 (§2.9). | 9480 delegates algorithms to RFC 9481. | ML-KEM-768 as MTI? Allow AES-256 and SHA-512 for ML-KEM-1024 / CNSA 2.0. Decide whether AuthEnvelopedData (AES-GCM) is in scope. |
| G10 | **Transport size** | §4.1: GET truncation and HTTP 414 errors. | n/a | PQC certs, signatures and ciphertexts are large. Require POST (`POSTPKIOperation`) for PQC messages. |
| G11 | **Backward compatibility** | Deployed clients are RSA-only. | 9810 keeps cmp2000 as the default unless v3 syntax is needed. | A CA must serve RSA and KEM clients side by side. The bag in G1 must not confuse legacy clients that pick the first cert (see the §3.5.2 note on Microsoft's server and keyUsage). |
| G12 | **Error handling** | failInfo values are badAlg, badMessageCheck and so on. | 9810 §5.1.3.4: decapsulation failure → badMessageCheck. | Map KEM failures onto existing failInfo values. Define when failInfoText may be used without becoming a decryption oracle. |
| G13 | **Security considerations** | n/a | 9810 §8.8 (the KEM must be IND-CCA2 because the key is reused, and every message needs a fresh encapsulation), §8.2 (only return decrypted values that are the expected type), §8.11 (with indirect POP, don't publish the cert, e.g. to CT logs, before confirmation). | Harvest-now-decrypt-later is the main reason confidentiality matters here: the challengePassword is inside the envelope. Keep the key-erasure text. Update §7.9 (SHA-1) and §7.6 (no POP on renewal) for the PQC case. |
| G14 | **IANA** | Existing registries for message types and capabilities | 9810 §9 | New GetCACaps keywords, possibly new messageTypes (for 3a), and new id-scep attributes or OIDs. |
